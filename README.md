# WISENSE

A reproduction of **"Tools and Methods for Achieving Wi-Fi Sensing in Embedded Devices"**
(Armenta-Garcia, Gonzalez-Navarro, Caro-Gutierrez, Garcia-Reyes — *Sensors* 2025,
[doi:10.3390/s25196220](https://doi.org/10.3390/s25196220)): human activity recognition
from Wi-Fi channel state information (CSI), collected and classified on ESP32s with no cloud.

Built on the authors' release ([Embedded_WiFi_Sensing](https://github.com/AlbanyArmenta0711/Embedded_WiFi_Sensing),
MIT), which has the dataset, the CSI collecting firmware and the trained models but **no
training code, no inference code, and no on-device deployment**. Those are what this repo adds.

Department of Electronics and Communication Engineering, Thapar Institute of Engineering &
Technology. Paper draft (IEEE Sensors Journal format): [`paper/`](paper/).

## What reproducing it found

The paper is light on detail; the released code and models fill it in. Five findings, each
with the command that shows it:

1. **The split is right, but the augmentation leaks it.** The authors hold out six whole
   subjects (s4–s9; recovered exactly from their `x_trn.npy` by `python -m tools.recover_split`
   — 1,198/1,198 samples matched, labels 100% agree). But `imf_sample_builder.py` recombines
   recordings from *all* subjects and `dataset_constructor.py` trains on all of them: 22 × 5 ×
   C(15,2) ≈ 11,550, against the paper's 11,513 synthetic samples. Held-out subjects' data was
   trained on. Here it is not.
2. **The model is trained per subcarrier.** Input is (850, 1). Every subcarrier of every
   recording is a separate sample; the paper's "all subcarriers" latency of 10,904 ms is
   exactly 47 × 232 ms, i.e. the single-subcarrier model run 47 times.
3. **The "problematic" subcarriers are raw 1 and 38–41.** The paper drops 52 → 47 without
   naming them. The published model scores 20–83% on those five and 88–95% on every other
   (`python -m tools.probe_published`). They are also the *most variable* after min-max
   normalisation — so "pick the highest-variance subcarrier" without excluding them picks the
   worst input. Our first attempt did exactly that.
4. **The headline numbers are float scores, and leaked.** Run as released, the small model
   scores **0.9243** per-subcarrier in *float* — the paper's 92.43%, which it reports as the
   *quantised* figure. The large model's float majority vote is **0.9755** — the paper's 97.55%.
   The released uint8 small model scores 0.9030.
5. **Model sizes differ from the paper.** The released uint8 files are 325 KB (small) and
   780 KB (large), not 127 KB and 277 KB.

## Results

Held-out subjects s4–s9, 449 recordings (21,103 per-subcarrier samples). Small model
(LSTM-Embedded DenseNet, 122,383 params), trained with the paper's settings exactly: 300
epochs, full pass per epoch, Adam 1e-4, batch 32, 47 subcarriers, EEMD synthetic set — on a
Kaggle T4, 3 sessions resumed from checkpoints. `artifacts/small_paper/evaluation.json`.

**Paper protocol** — synthetic training samples include the test subjects' recordings, as the
authors' scripts do. This is the comparable number, *not* a clean held-out score.

| | per subcarrier | one subcarrier (device) | vote over 47 |
|---|---|---|---|
| **Ours, float** | **0.9456** | **0.9354** | **0.9710** |
| Authors' released model, float | 0.9243 | 0.9198 | 0.9688 |
| **Ours, uint8** | 0.8982 | **0.9087** | 0.9510 |
| Authors' released model, uint8 | 0.9030 | 0.8797 | 0.9577 |
| Paper claims | 97.33% float · 92.43% uint8, single subcarrier | | |

- Float: ours beats the released model on all three scorings.
- uint8: on the device path (one subcarrier) ours is 2.9 points ahead of the released model;
  per-subcarrier and vote are within 0.7 points. Quantisation costs ~4–5 points, in line with
  the paper's "~4%". *Sit down* suffers most (0.91 → 0.76 per subcarrier).
- The paper's 92.43% "uint8" figure equals the released model's **float** per-subcarrier
  score (finding 4), so the like-for-like uint8 target is the released model's, above.
- Model file 322 KB uint8, same as the released 325 KB — not the 127 kB the paper states.

**Clean protocol** — identical training, but synthetic samples come from the 16 training
subjects only, so the score is subject-independent. Two seeds, 300 epochs each
(`artifacts/small_clean_s0`, `small_clean_s1`):

| | per subcarrier | one subcarrier (device) | vote over 47 |
|---|---|---|---|
| **Clean, float** (mean, range) | **0.526** (0.512–0.541) | **0.533** (0.517–0.550) | **0.576** (0.559–0.592) |
| Clean, uint8 | 0.475 (0.474–0.477) | 0.470 (0.452–0.488) | 0.515 (0.510–0.519) |

**Removing the leak costs about 40 points.** Training accuracy is still 97–98%: the model fits
the people it trains on and generalises poorly to new ones. Walking transfers best (0.80–0.88
recall), lying down worst (0.17–0.39).

Our paper-protocol model is statistically indistinguishable from the released one except for
float per-subcarrier accuracy (+2.1 points, 95% CI +0.2 to +4.0; `tools/stats.py`). A larger
quantisation calibration set *increases* the 8-bit loss (`tools/quant_study.py`).

## Quick start (host, no hardware)

```bash
# once: the authors' repo next to this one, with LFS
git lfs install
git clone https://github.com/AlbanyArmenta0711/Embedded_WiFi_Sensing.git ../Embedded_WiFi_Sensing

# venv OUTSIDE OneDrive -- TensorFlow in a synced folder is unusably slow
py -3.12 -m venv %USERPROFILE%\venvs\wisense
%USERPROFILE%\venvs\wisense\Scripts\activate
set WISENSE_CACHE=%USERPROFILE%\wisense_data      # caches (GBs) also outside sync folders
pip install -r requirements.txt

python -m wisense.data --check        # parse + cache (~2 min), print the split
python -m tools.recover_split         # prove which subjects the paper held out
python -m tools.probe_published       # score the authors' models; find the 47
pytest tests/                         # 24 tests

python -m wisense.augment             # EEMD, 8 of 47 subcarriers (~75 min, 11 cores)
python -m wisense.train --arch small   # ~2 h on CPU at the default budget
python -m wisense.export artifacts/small     # uint8 .tflite + firmware/…/generated/
python -m wisense.evaluate artifacts/small

mingw32-make -C firmware test         # C preprocessing vs frozen host reference
```

**Compute budget.** The paper trained 300 epochs over ~600k per-subcarrier samples on an
RTX 4060 Ti. On a 12-thread laptop CPU, training runs at ~170 samples/s and EEMD at ~5 s per
series, so the defaults are scaled down: EEMD on 8 evenly spaced subcarriers, and 150 epochs
of 8,000 freshly drawn samples. `--subcarriers 47` and `--epochs/--per-epoch` restore more of
it overnight. Report the budget alongside any number.

## Hardware

Three boards. The paper's layout — separate collection and inference — is kept:

```
 ESP32 #1 (Tx)  ~~~ Wi-Fi, ch 1, 50 pps ~~~>  ESP32 #2 (Rx)  --UART-->  ESP32-S3 N16R8
 collecting tool                              collecting tool            firmware/esp32s3_har
                                              (or USB -> host/csi_capture.py)
```

### 1. Toolchain: PlatformIO
Both firmware projects build with PlatformIO as plain ESP-IDF projects (`framework =
espidf`; platform espressif32 6.12.0 bundles ESP-IDF 5.5 — the authors used 5.4.1). No
separate ESP-IDF install. `pio` lives at `%USERPROFILE%\.platformio\penv\Scripts\pio.exe`
if it is not on PATH. First build downloads the framework (~1 GB).

### 2. Flash the collecting tool to both ESP32s
The authors' repo ships no PlatformIO config and no sdkconfig. Ours adds both:

```bash
python -m tools.install_collecting_tool      # copies firmware/collecting_tool/* into their tool dir
cd ../Embedded_WiFi_Sensing/ESP32_CSI_Web_Collecting_Tool
pio run -t upload -t monitor                 # once per board, same build for both
```

`sdkconfig.defaults` turns on what the tool cannot run without: **Wi-Fi CSI** (compiled out
by default — `esp_wifi_set_csi` fails otherwise), their **custom 2 MB-app partition table**,
and a **1 kHz FreeRTOS tick** (the packet timer and informer run in ticks). If you have
built it before, delete `sdkconfig.esp32` so the defaults apply.

Note each board's MAC from the boot log (`station initialized! MAC: …`).

### 3. Configure them through the web form
Each unconfigured board starts an AP: SSID `CSI_Collecting_ESP32`, password `root1234`.
Join it from a phone or laptop, browse to `http://192.168.1.1`.

- **Tx board:** Operation mode *Transmitter*, 20 MHz, packet rate **50**, channel **1**.
- **Rx board:** Operation mode *Receiver*, same bandwidth/rate/channel, MAC address = **the
  Tx board's MAC** (the Rx discards CSI from anyone else). Sample representation **Binary**.
  Tick only **"Length of CSI data"** and **"CSI buf"**. Then the informer mode:
  - *CONSOLE* → USB to the PC, for `host/csi_capture.py` (115200 baud).
  - *UART SERIAL COMMUNICATION* → to the S3: baud **921600**, TX pin of your choice.

The configuration is stored in NVS; the reset button (see the tool's `reset_button.c`)
erases it.

Place the boards a few metres apart with the activity area between them; the dataset was
collected in a computer lab with one person present.

### 4. Check the stream, record, classify on the PC
```bash
python host/csi_capture.py stats --port COM5          # expect ~50 pps
python host/csi_capture.py record --port COM5 --activity WA --subject s25
python host/csi_capture.py live --port COM5 --model artifacts/small/model_uint8.tflite
python host/csi_capture.py live --simulate --model ...  # no boards: replays held-out data
```
`stats` reporting 0 pps with log lines visible usually means CSI frames are not 128 bytes
(HT-LTF): the parser counts and skips them, because the model was trained on 128-byte frames.

Recording people other than yourself is human-subjects data collection: get your
institution's ethics approval and each participant's informed consent first.

### 5. The S3: on-device inference
Wiring: Rx ESP32 UART TX pin → S3 **GPIO18**, and GND ↔ GND.

```bash
python -m wisense.export artifacts/small     # writes firmware/esp32s3_har/main/generated/
cd firmware/esp32s3_har
pio run -t menuconfig    # optional -- WiSense HAR: arena, RX pin, baud, hop
pio run -t upload -t monitor
```
`platformio.ini` targets an S3 N16R8 (16 MB flash, octal PSRAM). For a different S3 module,
change the flash size there and the PSRAM mode in `sdkconfig.defaults`; delete
`sdkconfig.esp32s3_n16r8` afterwards so the change takes effect.
At boot it runs the **benchmark** — 25 held-out recordings compiled into flash — and prints
accuracy, per-inference latency and tensor-arena use: the paper's 232 ms / 127 kB claims,
checked without a radio. Then it switches to **live** classification of the UART stream,
once per second.

## Design notes

**Host and device run the same preprocessing, and a test proves it.** `csi_dsp.c` is checked
against a frozen output of `wisense/csi.py` + `features.py` from a real recording, pushed far
enough to wrap the ring buffer (`python -m tools.gen_csi_reference` regenerates it). If the C
test fails after a Python change, the board would be classifying a different signal than the
model was trained on.

**`wisense/models.py` is weight-exact.** `tests/test_models.py` loads the authors' trained
weights into the rebuilt graph by layer name and requires identical outputs. Architecture
details that the paper's prose gets wrong — the transitions output a fixed 5 channels, with no
ReLU — come from the published config, not from guesswork.

**Subcarrier selection uses doubles on the device.** It matches the host's float64 exactly;
the S3 has no double FPU, so it costs a few tens of ms per classification. That is small next
to inference, and a float/double disagreement on which subcarrier wins would be invisible.
